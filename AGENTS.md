# AGENTS.md: SyncBreaker

A cyberpunk-themed browser game built as a Computer Graphics final project. Plain JavaScript and HTML5 Canvas, no build step, no framework.

## Run & test
- Run: serve the repo root statically, e.g. `python3 -m http.server 8791`, and open `http://localhost:8791`.
  Avoid port 8765: the browser cache there holds another site's `js/main.js`.
- Tests: `node tests/run.js`. This is a zero-dependency runner. All tests must pass before every commit.
- Adding a new JS file: add a `<script>` tag to `index.html` in dependency order, and add the file to the relevant list in `tests/harness.js`.
- **Cache busting:** local scripts and the stylesheet in `index.html` carry a `?v=YYYYMMDD` query string (add `-2`, `-3`… for a second release the same day). Bump it on every release. Otherwise a player's browser can mix old and new files and crash.

## Git & deploy
- **The live site (syncbreaker.dormhi.com) is published from the `v2` branch.** A push to `v2` is a release. Only push when the user asks.
- Never add attribution or "generated by" lines to commits, PRs or comments.

## Architecture (essentials)
- Every file is a global class or object. They are loaded in order by `index.html`. `js/main.js` is the entry point.
- Logical canvas size is `VIEW` (960×640, `js/utils.js`). The backing store is scaled by the screen's pixel density (max 2×) in `main.js`, so layout, drawing and input always use `VIEW.W` / `VIEW.H`, never `canvas.width` / `canvas.height`.
- `js/core/GameLoop.js`: fixed 60 Hz simulation steps, accumulator, render interpolation via `alpha`.
  - Simulation state may only change in `update(fixedDt)`.
  - `render` is pure: it must not change state.
- `js/core/InputManager.js` unifies keyboard and pointer input. Sub-frame input offsets are passed to mechanics (`_pendingInputOffset`).
- `js/StateManager.js` holds the states: MENU, HUB, ACT, LEVEL, MINIGAME, LOCKPICK, GAME_OVER, ENDLESS, …
- `js/GameManager.js` registers every state and connects the flows.
- Mechanics follow the `Mechanic` contract (`js/mechanics/Mechanic.js`). Non-bar games run in the generic `MINIGAME` state:
  - `render(ctx, W, H, gameTime, alpha)`
  - `handleKey(code, offset)` and `handlePointer(x, y, phase, offset)`
  - `result` (`'success'` or `'fail'`) and `score`
- Physics: `js/core/PhysicsWorld.js` wraps Matter.js (`vendor/matter.min.js`).
  - Fixed step, prev→current interpolation, units in px/s.
  - Used only by physics games. The timing bar and the lockpick never use it.
- Timing bar motion is analytic (`TimingBarMechanic`), so it is deterministic and frame-rate independent.

## Campaign (current direction)
Full plan and decisions: **`docs/ACT_PLAN.md`**. Read it before touching progression, the HUB or difficulty.

- There are **9 acts** (raised from 6 on 2026-10-21). Each act is one game, and its 3–5 stages are that game's rising difficulty tiers.
- Finishing all stages of an act completes the act. A gate (Packet Purge, getting harder each time) sits between consecutive acts.
- Acts:
  1. REMOVE_MALWARE: Timing Bar, 4 stages, 8/10/14/18 hits
  2. REBUILD_FIREWALL: Stack Overflow, 3 stages, height 5/7/9 blocks, crane speed 1.30/1.36/1.42
  3. CLOSE_PORTS: Orbital Shield, 4 stages, 12/16/20/20 packets on 4/6/8/8 ports, lives 4/5/6/7 (`js/mechanics/OrbitalShieldMechanic.js`)
  4. RESET_CREDS: Signal Lock, 5 stages (EASY…EXPERT), 3/3/4/4/5 keys against a timer; revive = +20 s (`js/mechanics/SignalLockMechanic.js`)
  5. TRACE_LOGS: Route Trace, 3 stages (4×4 / 5×5 / 6×6 grids, 2/3/3 traces against a timer); revive = +20 s (`js/mechanics/RouteTraceMechanic.js`)
  6. CUT_ACCESS: in development
  7. DEFUSE_PAYLOAD: in development
  8. RESTORE_CORE: in development
  9. FINAL_AUDIT: in development. Decided: the final act tests **knowledge and reasoning only**, with no timer and no lives
- The mechanics of acts 6–9 are **not decided yet** (beyond the notes above). They are designed together with the user, one phase at a time. Do not invent and ship them.
- The lockpick is used only for revives (Timing Bar, Orbital Shield, Signal Lock, Route Trace and Endless). A revivable mechanic game implements `revive()`; the run resumes in the MINIGAME host with `resume: true`. Endless unlocks after the final act (`CAMPAIGN.finalAct`, now 9), and players who already unlocked it keep it.
- **Endless Mode will change.** Today it is Timing Bar only. The goal is an endless mode that supports **all** campaign games. It is not planned yet and will be planned with the user later (plan section 8b). Meanwhile, design new games so their difficulty can keep ramping and they produce a score.
- Data lives in `js/data/Campaign.js`. Progress, lock rules and the migration from the old save format live in `js/CampaignProgress.js` (save key `sb_campaign_v1`).
- Phase status: Phase 1 (campaign + Acts 1–2 + Gate 1), Phase 2 (Act 3 Orbital Shield + Gate 2) and Phase 3 (Act 4 Signal Lock + Gate 3) are implemented. The campaign was then extended to 9 acts (gates 1–8). Phase 4 (Act 5 Route Trace + Gate 4) is implemented. Next: Act 6.
- HUB act map = a carousel (`_mapIndex` / `_mapScroll`): progress rail on top (with PERIMETER / INTERNAL / CORE brackets), the focused act as a big game card (`_drawActCard`), neighbours peeking, a firewall wall at each gate (`_drawGateWall`, double between layers). Cards and gates are drawn by `_renderActMap`; their tap targets are hidden buttons rebuilt by `_mapGo`.
  - Touch drag: `InputManager` lets the host claim a touch as a drag (`onDragStart` / `onDragMove` / `onDragEnd`); the HUB claims touches on the card band (`_mapDragStart`). A release that barely moved is a tap (resolved on release); otherwise the carousel snaps, and a quick flick moves one act. The background shifts with the carousel (`_bgShift` parallax).
- Act screen = a rising stage ladder (`_actScreenLayout`): cards climb left to right, a circuit track (`_drawStageTrack`) runs under them to the gate node. `_stageView` decides cleared / next / locked. The first clear of a stage plays a one-time track fill + unlock effect (`_ladderAnim`, advanced in the ACT `update`, dropped on exit).
- Operator status: `CampaignProgress.clearanceLevel()` (acts fully cleared, shown as `UITheme.clearanceLabel`, e.g. L4 OPERATOR) and `integrity()` (0..1, each act an equal share filled by its cleared stages). Shown on the menu and the HUB; clearing an act shows "CLEARANCE GRANTED" once on the act screen (`_clearanceUp`). The main menu gets more corrupted the lower the integrity.
- Stage stars: rules in `CAMPAIGN.starRules` / `CAMPAIGN.starsFor` (`js/data/Campaign.js`, approved 2026-10-23, docs/UI_PLAN.md 3e). Each game exposes `starStats()` (Timing Bar: `LevelManager.starStats()`); a revive caps a run at 1 star. Best stars per stage are saved (`completeStage(…, stars)`, `stageStars`, `actStars`); the host shows them on the result panel (`_beginResultStars` / `_drawResultStars`), on cleared stage cards and as an act total on HUB cards. Do not change the thresholds without the user's approval and a bot sweep.
- Polish: screen changes are a soft eased fade through dark with a thin centre line (`StateManager._renderTransition`, at most two fills a frame). A shutter + glitch wipe was tried and dropped on 2026-10-23: tiring to look at and it stuttered on phones; keep transitions calm and cheap. Stage clears stamp ACCESS GRANTED on the result panel; a freshly cleared act gets its SECURED stamp slammed on the HUB card (`_securedAnim`). Interface sounds: `Sound.playClick` (buttons, not the in-game pause), `playWhoosh` (screen change), `playStamp`, `playStar(k)`.
- Reduced motion: `UITheme.reducedMotion` follows the OS `prefers-reduced-motion`. New effects must check it: no glitch, parallax, pops, slams or ladder fill; transitions become a plain fade; card animations freeze.
- Network layers (PERIMETER 1–3 / INTERNAL 4–6 / CORE 7–9, `UITheme.layers`) tint the background: `_bgLayerTarget()` picks the layer of the screen (HUB = focused act, act screen and games = their act, menu = PERIMETER), `_bgLayer` eases toward it, and `<body data-layer>` lets CSS colour the page around the canvas.
- Hold-to-play games set `wantsHold = true` and implement `handleKeyUp`, `handlePointer(…, 'up')` and `releaseAll()`. `InputManager` delivers key-up, mouse-down, pointer-up (also off-canvas) and window blur. The host never turns the click that follows a mouse hold into a new press.

## Pause & back navigation
- Every in-game screen (LEVEL, MINIGAME, LOCKPICK, ENDLESS) has a ⏸ button (`_addLeaveButton(cfg)`, bottom-left). It opens the PAUSED panel: RESUME / RESTART (campaign stages only) / LEAVE. RESTART and LEAVE always ask first, and the safe choice is focused. The game is frozen while the panel is open.
- Esc and the browser/phone back gesture walk the same panel (`_pauseBack`): open the panel → step back from a warning → resume.
- `js/core/BackGuard.js` keeps one guard entry in the browser history. This covers Android back, iOS edge swipe, the desktop back button and Safari's two-finger swipe: they pop the guard, and `GameManager.handleBrowserBack()` steps back one screen. On the menu, the first back shows "Press back again to leave"; only a second back within 2.5 s leaves the site.
- Chrome skips history entries pushed without user interaction, so the guard is first armed on the player's first tap or key press.

## Orientation
- The game is landscape-only for now (960×640 canvas). On touch devices held upright a CSS overlay (`.sb-rotate`) asks the player to rotate, and `main.js` pauses the loop (`GameLoop.setPaused`).
- A real portrait layout is planned as a separate phase (plan section 8a). Until then, new screens only need to work in landscape (phone ~844×390 and desktop).
