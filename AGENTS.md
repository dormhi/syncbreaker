# AGENTS.md: SyncBreaker

A cyberpunk-themed browser game built as a Computer Graphics final project. Plain JavaScript and HTML5 Canvas, no build step, no framework.

## Run & test
- Run: serve the repo root statically, e.g. `python3 -m http.server 8791`, and open `http://localhost:8791`.
  Avoid port 8765: the browser cache there holds another site's `js/main.js`.
- Tests: `node tests/run.js`. This is a zero-dependency runner. All tests must pass before every commit.
- Adding a new JS file: add a `<script>` tag to `index.html` in dependency order, and add the file to the relevant list in `tests/harness.js`.
- **Cache busting:** local scripts and the stylesheet in `index.html` carry a `?v=YYYYMMDD` query string (add `-2`, `-3`… for a second release the same day). Bump it on every release. Otherwise a player's browser can mix old and new files and crash.

## Git & deploy
- **The live site (syncbreaker.dormhi.com) is published from the `v2` branch.** A push to `v2` is a release. Only push when the user asks.
- Never add attribution or "generated by" lines to commits, PRs or comments.

## Architecture (essentials)
- Every file is a global class or object. They are loaded in order by `index.html`. `js/main.js` is the entry point.
- `js/core/GameLoop.js`: fixed 60 Hz simulation steps, accumulator, render interpolation via `alpha`.
  - Simulation state may only change in `update(fixedDt)`.
  - `render` is pure: it must not change state.
- `js/core/InputManager.js` unifies keyboard and pointer input. Sub-frame input offsets are passed to mechanics (`_pendingInputOffset`).
- `js/StateManager.js` holds the states: MENU, HUB, ACT, LEVEL, MINIGAME, LOCKPICK, GAME_OVER, ENDLESS, …
- `js/GameManager.js` registers every state and connects the flows.
- Mechanics follow the `Mechanic` contract (`js/mechanics/Mechanic.js`). Non-bar games run in the generic `MINIGAME` state:
  - `render(ctx, W, H, gameTime, alpha)`
  - `handleKey(code, offset)` and `handlePointer(x, y, phase, offset)`
  - `result` (`'success'` or `'fail'`) and `score`
- Physics: `js/core/PhysicsWorld.js` wraps Matter.js (`vendor/matter.min.js`).
  - Fixed step, prev→current interpolation, units in px/s.
  - Used only by physics games. The timing bar and the lockpick never use it.
- Timing bar motion is analytic (`TimingBarMechanic`), so it is deterministic and frame-rate independent.

## Campaign (current direction)
Full plan and decisions: **`docs/ACT_PLAN.md`**. Read it before touching progression, the HUB or difficulty.

- There are 6 acts. Each act is one game, and its 3–5 stages are that game's rising difficulty tiers.
- Finishing all stages of an act completes the act. A gate (Packet Purge, getting harder each time) sits between consecutive acts.
- Acts:
  1. REMOVE_MALWARE: Timing Bar, 4 stages, 8/10/14/18 hits
  2. REBUILD_FIREWALL: Stack Overflow, 3 stages, height 5/7/9 blocks, crane speed 1.30/1.36/1.42
  3. CLOSE_PORTS: Orbital Shield, 4 stages, 12/16/20/20 packets on 4/6/8/8 ports, lives 4/5/6/7 (`js/mechanics/OrbitalShieldMechanic.js`)
  4. RESET_CREDS: in development
  5. TRACE_LOGS: in development
  6. CUT_ACCESS: in development
- The mechanics of acts 4–6 are **not decided yet**. They are designed together with the user, one phase at a time. Do not invent and ship them.
- The lockpick is used only for revives (Timing Bar, Orbital Shield and Endless). A revivable mechanic game implements `revive()`; the run resumes in the MINIGAME host with `resume: true`. Endless unlocks after Act 6, and players who already unlocked it keep it.
- **Endless Mode will change.** Today it is Timing Bar only. The goal is an endless mode that supports **all** campaign games. It is not planned yet and will be planned with the user later (plan section 8b). Meanwhile, design new games so their difficulty can keep ramping and they produce a score.
- Data lives in `js/data/Campaign.js`. Progress, lock rules and the migration from the old save format live in `js/CampaignProgress.js` (save key `sb_campaign_v1`).
- Phase status: **Phase 1** (campaign + Acts 1–2 + Gate 1) and **Phase 2** (Act 3 Orbital Shield + Gate 2) are implemented. Phases 3–5 add acts 4–6 one by one.

## Leaderboard / Supabase
- Endless leaderboard on Supabase (`js/LeaderboardService.js`). Every browser is an anonymous user. An **operator** (unique name + password) can be played from any browser.
- SQL lives in `supabase/` and is applied **by the user** in the Supabase SQL Editor. Never run anything against the live project.
  Test SQL against a local Postgres instead: stub the `auth` schema and the roles.
- Operator name + password UI: `js/ProfileForm.js`, a DOM overlay with real inputs (works with mobile keyboards and password managers).

## UI helpers
- `js/TipBar.js`: one dim rotating hint line on the HUB and act screens. Tips have desktop and touch variants, chosen by `InputManager.mode`.
- Field guide: the `GUIDE` state in `GameManager` (`GameManager.GUIDE_PAGES`). Opened with the `?` button or the H key.
